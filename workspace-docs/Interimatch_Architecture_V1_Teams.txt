INTERIMATCH SANTE - ARCHITECTURE BACKEND V1
Equipe : 4 personnes | Duree : 11 jours | Rendu a date fixe

Architecture cible a developper. Ce document ne declare pas
l'application ni les integrations deja operationnelles.

1. SCHEMA GENERAL

 [Infirmier / Etablissement / Agence]
                   |
                   v
          [Entree HTTPS unique]
                   |
          +--------+---------+
          |                  |
          v                  v
 [Frontend Next.js]   [API NestJS modulaire]
                             |
           +-----------------+------------------+
           |                 |                  |
           v                 v                  v
 [PostgreSQL + PostGIS]   [MongoDB]    [Documents prives chiffres]
  Donnees metier         Explications  RIB, justificatifs,
  et evenements          du matching  confirmations

 Integrations du backend :
 +-------------------------+     +---------------------------+
 | API NestJS              |---->| France Travail / FINESS   |
 |                         |     | Import et normalisation   |
 |                         |---->| API Annuaire Sante RPPS   |
 |                         |     | Recherche du numero       |
 |                         |<--->| n8n : trois automatisations|
 +-------------------------+     +---------------------------+

- PostgreSQL est la base de reference : comptes, profils, disponibilites,
  missions, candidatures, affectations, notifications et evenements.
- PostGIS ajoute la recherche par distance a PostgreSQL.
- MongoDB conserve les explications du matching.
- NestJS applique les regles metier et les autorisations.
- Le frontend affiche les donnees et les actions permises.
- n8n orchestre les automatisations via des appels API internes.
- Les bases, documents et l'administration n8n restent prives.
- Les echanges sensibles du deploiement sont proteges par TLS.
- La CLI partage les services d'import ; pas de second pipeline.

2. STACK RETENUE

Runtime          : Node.js 24 LTS + TypeScript
Backend          : NestJS avec adaptateur Express
API              : REST /api/v1 + OpenAPI
Base metier      : PostgreSQL + PostGIS + btree_gist
Acces SQL        : TypeORM + migrations SQL versionnees
Base complement. : MongoDB avec Mongoose
Authentification : Sessions serveur PostgreSQL + Argon2id
Documents        : Stockage prive + chiffrement AES-256-GCM
Automatisation   : n8n + outbox PostgreSQL
Import public    : CLI Commander.js
Frontend         : Next.js + TypeScript
Livraison        : Docker Compose + CI + reverse proxy HTTPS
Tests            : Jest, Supertest et bases reelles isolees

Le backend reste UNE application organisee en modules.
Les versions exactes et leur compatibilite seront figees au bootstrap.

4. LES TROIS AUTOMATISATIONS F12

 [Mission compatible] --> [n8n] --> [Notification a l'infirmier]

 [Affectation validee] -> [n8n] --> [Confirmation PDF generee]
                                          |
                                          v
                              [Document prive + notification]

 [Mission non pourvue] -> [n8n] --> [Relance du responsable]

Le backend genere la confirmation depuis un modele.
La confirmation n'est pas un contrat signe ; contrats complets en V3.
L'outbox est enregistree avec la transaction metier.
Les reprises sont prevues ; les doublons ne recreent pas les actions.

5. CONTROLE RPPS F18

 [Saisie ou modification du numero RPPS]
                    |
                    v
      [Consultation API Annuaire Sante]
                    |
       +------------+------------+
       |            |            |
       v            v            v
   [Retrouve]  [Non retrouve] [Indisponible]
       |            |            |
       v            v            v
 [Condition     [Blocage]     [En attente]
 RPPS satisfaite]                |
                                 v
                         [Nouvelle tentative]

Blocage / attente : candidature et nouvelle affectation internes.
Le profil reste accessible pour corriger le numero.
Une panne n'est jamais assimilee a un numero invalide.
Un RPPS retrouve ne prouve pas l'identite ni toutes les qualifications.
Pas de validation manuelle RPPS par l'agence ajoutee.
Attestation sur l'honneur : V2. References : hors V1, V2 envisagee.

10. CONTROLES ESSENTIELS

- Une seule affectation active par mission.
- Aucun chevauchement incompatible connu pour un infirmier.
- Consentement lie a la version actuelle de la mission.
- Annulation simultanee de la mission et de l'affectation.
- Permissions verifiees sur chaque action et document.
- RPPS non retrouve : blocage ; service indisponible : attente.
- Import API reel, nettoye et utilise dans le produit.
- Ecriture ET lecture reelles dans PostgreSQL et MongoDB.
- Trois workflows executes, testables et rejouables.
- Tests unitaires/fonctionnels et rapport de couverture livres.

Les acces API authentifies et la realisation restent a prouver.
Le planning fixe le travail cible ; il ne declare aucun test reussi.
