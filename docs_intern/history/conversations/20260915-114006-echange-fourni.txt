Voici l’architecture V1 retenue, pour 4 personnes sur 11 jours. Le backend reste une seule application NestJS organisée en modules.
```mermaid
flowchart LR
    user["Infirmier / Établissement / Agence"]
    proxy["Entrée HTTPS"]
    front["Frontend Next.js"]
    api["Backend NestJS modulaire"]
    sql[("PostgreSQL + PostGIS")]
    mongo[("MongoDB")]
    files["Documents privés chiffrés"]
    n8n["n8n : 3 automatisations"]
    external["France Travail / FINESS"]
    rpps["API Annuaire Santé RPPS"]

    user --> proxy
    proxy -->|"Pages"| front
    proxy -->|"/api/v1"| api

    api -->|"Données métier + outbox"| sql
    api -->|"Explications du matching"| mongo
    api -->|"RIB, justificatifs, confirmations"| files

    api -->|"Événements après validation"| n8n
    n8n -->|"Actions internes autorisées"| api

    api -->|"Import et normalisation"| external
    api -->|"Recherche du numéro"| rpps
```



PostgreSQL est la base de référence : comptes, profils, disponibilités, missions, candidatures, affectations et notifications. PostGIS ajoute la recherche par distance. MongoDB conserve les explications du matching.
NestJS prend toutes les décisions métier. Le frontend affiche les résultats ; n8n orchestre les automatisations. Les bases et les documents restent privés.
Le backend sera organisé ainsi :
backend/
└── src/
    ├── auth/                       Connexion, sessions
    ├── organizations/              Établissements, agences, droits
    ├── profiles/                   Profils et qualifications
    ├── facilities/                 Établissements et FINESS
    ├── availability/               Disponibilités et mobilité
    ├── missions/                   Création, publication, états
    ├── applications/               Candidatures et consentements
    ├── assignments/                Affectations et annulations
    ├── search/                     Filtres et distances
    ├── favorites/                  Offres et établissements favoris
    ├── matching/                   Éligibilité et score explicable
    ├── professional-verification/  Contrôle RPPS
    ├── documents/                  RIB et justificatifs chiffrés
    ├── mission-confirmations/      Génération des confirmations
    ├── notifications/              Notifications internes
    ├── public-data/                Imports API et commande CLI
    ├── automation/                 Événements, reprises et n8n
    ├── dashboards/                 Tableaux de bord
    └── audit/                      Historique des actions sensibles
Les trois automatisations F12 sont :
Déclenchement	Résultat
Une mission correspond au profil	Notification à l’infirmier
Une affectation est validée	Confirmation générée depuis un modèle
Une mission reste non pourvue	Relance du responsable


Pour F18 — RPPS :
```mermaid
flowchart LR
    input["Saisie du RPPS"] --> api["Consultation API"]
    api --> found["Retrouvé"]
    api --> missing["Non retrouvé"]
    api --> unavailable["Service indisponible"]

    found --> allowed["Condition RPPS satisfaite"]
    missing --> blocked["Candidature et nouvelle affectation bloquées"]
    unavailable --> pending["En attente + nouvelle tentative"]
```



Un RPPS retrouvé ne remplace pas les autres contrôles de qualification et de disponibilité. L’infirmier garde accès à son profil pour corriger son numéro.
Le plan de construction suit ces étapes, avec travail en parallèle :
Étape	Résultat attendu
1	Dépôt, démarrage local, schéma des données, contrats API et accès fournisseurs
2	Connexion, profils, organisations et création des missions
3	Recherche, calendrier, favoris et matching
4	Candidatures, consentements et affectations protégées contre les doublons
5	RPPS, import public et documents chiffrés
6	Trois automatisations et confirmation PDF
7	Recette complète, corrections, coverage et démonstration


La répartition proposée à quatre :
Responsable	Périmètre principal
A	Backend métier : comptes, missions, candidatures, affectations
B	Données : recherche, matching, RPPS, imports et CLI
C	Frontend : parcours, calendrier, dashboards, responsive
D	Infrastructure, documents chiffrés, confirmation et n8n


Chacun teste ses modules ; l’intégration et la recette sont collectives.
